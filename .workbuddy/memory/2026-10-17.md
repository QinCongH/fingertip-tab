## 修复 `npm run tauri dev` 报错：cargo program not found

### 问题现象
```
failed to run 'cargo metadata' command to get workspace directory:
failed to run command cargo metadata --no-deps --format-version 1: program not found
```

### 根因（两个独立问题）
1. **Rust 工具链缺失** — `C:\Users\Administrator\.rustup` / `.cargo` 整个目录不存在。
   证据：`src-tauri/target/.rustc_info.json` 显示此前用的是 rustc 1.99.0 MSVC，
   而 `release/fingertip-tab.exe`(9/16) 与 `debug/fingertip-tab.exe`(10/6) 说明以前能正常构建，
   说明工具链是被清理/卸载了，**与项目代码无关**。
2. **MSVC 编译器缺失** — 全盘无 `link.exe`，无任何 Visual Studio / Build Tools。
   Tauri 在 Windows 必须依赖 MSVC linker，即使装好 Rust 也无法链接。

### 环境排查结论
- `tauri.conf.json` / `Cargo.toml` / `node_modules/@tauri-apps/cli` 均正常，无需改动
- 前端 `npm run build` 独立验证通过（8.36s），纯前端链路无问题
- WebView2 Runtime 已存在：155.0.4283.62 ✓

### 关键障碍：重复的 proxy 环境变量
安装 VS Build Tools 时引导程序崩溃：
```
Error 0x80070057: Couldn't launch setup process.
已添加项。字典中的关键字:"http_proxy"所添加的关键字:"HTTP_PROXY"
  at System.Diagnostics.ProcessStartInfo.get_EnvironmentVariables()
```
环境变量中同时存在 `HTTP_PROXY` 与 `http_proxy`（均为 `http://127.0.0.1:52339`），
.NET 复制环境变量时视为重复键直接抛异常。**该问题会连带击穿 `Start-Process` 与
`Get-ChildItem Env:`**（PowerShell 自身也报 ArgumentException）。

绕过方式：用 `System.Diagnostics.ProcessStartInfo` 手工构建干净环境变量表
（`UseShellExecute=$false`，逐项 Add，代理只保留大写），
脚本落盘于 `D:\software\tools\installer\install_vs.ps1`。
注意：执行需 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File`（系统执行策略禁止 .ps1）。

### 根治 proxy 重复键（关键）
`ProcessStartInfo.EnvironmentVariables` 在本机 PS 5.1 上返回 null（同样被重复键击穿），
`Start-Process` 也直接抛异常。最终方案：**P/Invoke Win32 `CreateProcessW`**，
自行拼装去重后的环境块（`GetEnvironmentStringsW` 读取 → 过滤 → `CREATE_UNICODE_ENVIRONMENT`），
脚本：`D:\software\tools\installer\install_vs4.ps1`。此法 setup.exe 及其子进程
（如 Microsoft.Build.UnGAC）均不再报 0x80070057。

注意：User/Machine 级环境变量本来就干净，重复项是**进程级注入**的，
所以 `[Environment]::SetEnvironmentVariable(..., "User")` 删除无效。

### setup.exe 参数踩坑记录
直接调用 `C:\Program Files (x86)\Microsoft Visual Studio\Installer\setup.exe` 时，
参数校验逐级报错（exit code 87），最终可用组合为：
```
install --productId Microsoft.VisualStudio.Product.BuildTools
       --channelUri https://aka.ms/vs/17/release/channel
       --installChannelUri https://aka.ms/vs/17/release/channel
       --quiet --norestart --nocache --noUpdateInstaller
       --installPath "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools"
       --add Microsoft.VisualStudio.Workload.VCTools --includeRecommended
       --add Microsoft.VisualStudio.Component.VC.Tools.x86.x64
       --add Microsoft.VisualStudio.Component.Windows11SDK.22621
```
- `--wait` 是引导程序(vs_BuildTools.exe)的参数，setup.exe **不认**
- `--productId` 必须搭配 `--channelUri` / `--installChannelUri`
- 直接跑 `vs_BuildTools.exe` 时若报上述 proxy 错误，说明它已解包成功，
  可改调 `Installer\setup.exe` 绕过

### cargo 拉依赖卡死 → 配国内镜像
`cargo build` 挂在 `Updating crates.io index` 20 分钟无进展（cargo 只认小写 `http_proxy`，
而环境里是大写 `HTTP_PROXY`，导致直连超时）。
解决：新建 `C:\Users\Administrator\.cargo\config.toml`，用 rsproxy 稀疏索引：
```toml
[source.crates-io]
replace-with = 'rsproxy-sparse'
[source.rsproxy-sparse]
registry = "sparse+https://rsproxy.cn/index/"
[http]
proxy = "http://127.0.0.1:52339"
```
之后 `cargo fetch` 2 秒完成，`cargo build --offline` 2m17s 成功。

### rustup-init 卡死

并提示 `warn: installing msvc toolchain without its prerequisites`。
处理：Stop-Process 强杀后改用 `rustup toolchain install stable-x86_64-pc-windows-msvc --profile minimal` 补装，正常推进。

## 功能改造：设置「修改路径」→「切换工作区」

### 问题反馈
用户报错"迁移失败：目标目录不为空，为避免数据覆盖请选择空目录"，
并澄清真实需求：**该功能不是数据迁移，而是选定文件夹作为工作区加载**——
若目录符合曲谱库数据结构则加载它，否则将其初始化为新工作区。

### 语义决策（已与用户确认）
1. 非空且无 `FingertipTabs.db` 的目录 → 询问后初始化，不报错拒绝
2. 切换后原库数据**原地保留不动**，不做任何搬移，可随时切回

### 后端改动（`src-tauri/src/commands/settings.rs`）
- 删除 `migrate_library`（原逻辑：`file::move_path` 搬移 db/settings.json/Resources + 强制目标目录为空）
- 新增 `probe_library(&Path) -> LibraryProbe`（探测 exists/empty/has_db/has_resources）
- 新增命令 `probe_library_path`（前端预检用）
- 新增命令 `switch_library(app, state, new_path, init_if_missing)`：
  关闭旧 pool → `ensure_library_ready_at` 初始化目标目录 → 重建 share context → 更新 app config 指针
- 抽出 `ensure_library_ready_at(_app, lib)`，与 `ensure_library_ready(app)` 共用结构初始化逻辑
  （否则切库时会跳回默认路径，这是拆分的必要原因）
- 关键点：`share::register_context` 也持有 pool，必须一并重建
- 删除死代码 `utils/file.rs` 的 `move_path` + `copy_dir_recursive` + 随之失效的 `use std::fs`

### 前端改动
- `lib/tauri.ts`：`migrateLibrary` → `probeLibraryPath` + `switchLibrary`；新增 `LibraryProbe` 类型
- `SettingsView.vue`：`doMigrate` → `doSwitch`（选目录→探测→差异化弹窗）+ `confirmSwitch`
  - 三种确认态：`switch_load`（已有库）/ `switch_init`（空目录）/ `switch_newin`（非空无库，danger）
  - 用 `computed` 按 `pendingProbe` 动态生成标题文案
  - 切换后仍调 `restartApp()`，因 `AppState.pool` 无法热替换
- `i18n.ts`：中英文案全部重写，key 由 `settings.migrate_*` 改为 `settings.switch_*`
- 注意：该文件里配置对象是 `s`（`const s = settings.settings`），不是 store 本身

### 验证
`npm run build`（含 vue-tsc 类型检查）✅ 通过 5.18s；`cargo build --offline` ✅ 13.07s 无 warning。

（`config.json` 与用户曲谱库指针所在位置），改动会导致已安装用户「丢失」工作区。

## 修复两个运行时报错

### 1. Failed to fetch dynamically imported module: SettingsView.vue
**根因**：1420 端口无进程监听 —— dev server 已死（被中断的 tauri build 连带终止）。
非代码问题。重启 `npm run dev` 即可，实测 HTTP 200。

### 2. tesseract.js worker 加载失败（真实问题）
`https://cdn.jsdelivr.net/npm/tesseract.js@v7.0.0/dist/worker.min.js` 在本机网络**完全不通**
（curl 返回 HTTP 000，而普通站点正常）。原 `ocr.ts` 未指定任何路径，
tesseract.js 默认从 jsDelivr 拉 worker + WASM + 语言包 → OCR 整体不可用且离线必然失败。

**解决方案：OCR 资源全面本地化**
- `public/ocr/`：`worker.min.js` + tesseract-core 的 LSTM 系列 3 档 SIMD 变体（20MB）
- `public/ocr-lang/`：`chi_sim.traineddata.gz`(1.7MB) + `eng.traineddata.gz`(2.9MB)
  来源 npmmirror（jsDelivr 不可达时唯一可用镜像）：
  `https://registry.npmmirror.com/@tesseract.js-data/{lang}/-/{lang}-1.0.0.tgz`
  ⚠️ 该 .tgz 是 tar 归档，需解包取 `package/4.0.0_best_int/` 下的文件才是真正 traineddata
- `src/lib/ocr.ts` 的 `createWorker` 显式指定 `workerPath` / `corePath` / `langPath`

**裁剪依据**：`createWorker(..., 1, ...)` 第三参数为 1 = LSTM_ONLY，worker 按 SIMD 能力
三选一加载，故删除 legacy 与非 lstm 变体可省下约 20MB。

### 环境备注
- jsDelivr 不可用，npm 走 `registry.npmmirror.com`
- cargo 已配置 rsproxy 稀疏索引（`~/.cargo/config.toml`）
